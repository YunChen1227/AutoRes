Saturation point identification

In one sentence
The saturation point is the batch size or request rate beyond which adding more parallel work stops making your inference faster and starts making latency worse.
Team Note
@theneuralbase_teamverified April 2026 — vLLM 0.4.x, SGLang 0.3.0+✓ verified

Verified April 2026 - the saturation dynamics described apply across vLLM 0.4.x, SGLang 0.3.0+, and TensorRTLLM. Key production note: saturation point is NOT static - it shifts with model size, sequence length, and hardware.

A 7B model saturates at batch size ~64 on H100, but a 70B model saturates at ~8-16 on the same hardware due to KV cache memory growth. When measuring, fix sequence_length and vary batch_size independently; real workloads with variable lengths show saturation earlier.

The 80% buffer rule works well for SLA compliance but leaves 20% headroom only if your SLA permits pertoken latency to grow linearly with batch - confirm this assumption with your monitoring stack first. Token throughput (tokens/second) may still climb past saturation while pertoken latency rises: these are not contradictory - saturation is about latency efficiency, not absolute throughput.

Use vLLM's builtin metrics (get_model_config(), get_num_gpu_blocks()) to measure KV cache pressure directly rather than relying on inferenceonly benchmarks.

Apr 22, 2026

Background

Before continuous batching systems like vLLM (2023), inference servers operated on a request-level granularity: each request waited for a response before the next could start. This created a false choice: either serve one request at a time (wasting GPU) or batch requests and delay all of them equally (violating SLA). The saturation point became invisible because the tradeoff was implicit in the batching strategy itself. With token-level scheduling and PagedAttention, the saturation point became explicit and measurable: you could now see exactly when your system stopped being GPU-bound and became memory-bound or latency-bound instead.

Why this matters

Identifying saturation separates the regime where you're efficiently using GPU resources from the regime where you're just piling up work in memory. This distinction determines whether you scale horizontally, accept longer latencies, or reject requests: decisions that directly impact SLA compliance and operational cost.

How it works

What it is: The saturation point is the operating region where your inference system reaches an inflection: beyond it, marginal throughput gains come at disproportionate latency costs. Before saturation, adding batch size or concurrent requests improves system efficiency (more tokens/second per GPU). After saturation, you're adding tokens to memory but not accelerating their processing meaningfully: each token waits longer without corresponding speedup.

How it works: Modern inference systems exhibit three regimes. In the compute-bound region (low batch size), the GPU is underutilized: you have free compute cycles and can absorb more work nearly for free. In the saturation region (mid batch size), throughput scales roughly linearly with batch size because you're moving from idle compute to full utilization. In the memory-bound region (high batch size), adding more requests forces the system to manage larger KV caches and longer attention computations. The GPU's memory bandwidth becomes the bottleneck, not its compute cores. Token-level latency rises sharply because each token competes for memory bus access.

Why it works this way: Modern LLMs are fundamentally memory-bandwidth-bound during inference, not compute-bound. A single token's forward pass requires loading the entire model weights and KV cache from HBM (high-bandwidth memory). With N concurrent sequences of varying lengths, the KV cache memory requirement grows linearly. The attention operation itself is O(sequence_length²) in memory access per token. Below saturation, you have slack in this system: your KV cache footprint is small enough that memory bandwidth easily serves all sequences. Above saturation, memory bandwidth becomes contended. The system doesn't crash or slow proportionally; instead, queue depth grows (more requests waiting in the scheduler) while per-token latency stretches (each token waits longer for memory access).

What it enables: Identifying saturation precisely lets you make principled decisions: set your target batch size or concurrent request limit just below saturation to maximize throughput while respecting latency SLAs. It also reveals when to scale horizontally (spin up another inference server) versus when you've hit a hard memory limit and must reject or defer requests. For batch jobs, saturation identification tells you the maximum effective batch size; beyond it, wall-clock time doesn't improve.

Analogy

Picture a highway at different traffic densities. At light traffic (compute-bound region), adding more cars barely slows anyone down: the road has spare capacity. As traffic increases toward optimal density (saturation point), cars move at maximum speed and the road handles the most vehicles per hour. Beyond that density, you're not adding speed; you're adding congestion. Each car moves slower, not because the road got worse, but because cars now spend time waiting for exit ramps and merging space. The total vehicles per hour actually decreases even as the road gets more crowded, because latency: time to traverse the highway: has become unbearable.

Visualize it

Imagine a graph with batch size on the x-axis and per-token latency on the y-axis. The line starts high and steep (small batches, each token waits a long time because the GPU isn't fully loaded). As batch size increases, latency drops sharply: this is the compute-bound region where the GPU is hungry for work. Then the curve flattens and starts bending upward around a specific point: saturation. Beyond this point, latency climbs faster and faster. That inflection point: where the curve stops decreasing and starts increasing: that's saturation. You're looking for the elbow in the curve.

Common misconception

Wrong belief

Saturation means the system breaks or becomes unstable; if my batch size is below saturation, I should maximize it to get maximum throughput.

Why it's wrong

Saturation is not a cliff: it's a gradual transition. The system doesn't break. Instead, you enter a regime where latency costs outweigh throughput gains. Maximizing batch size up to saturation maximizes throughput, but violates latency SLAs. Saturation also varies with request distribution: long sequences saturate sooner than short ones because they consume more KV cache per token.

Saturation is a tradeoff frontier. Below saturation, you're trading batch size for latency at a favorable rate: small latency increase, large throughput gain. Above saturation, the tradeoff inverts: large latency increase, small throughput gain. Your operating point should be chosen based on your SLA, not based on maximizing throughput. Most production systems intentionally operate well below saturation to guarantee tail latencies.

Connect to practice

You've already seen this working when you experimented with batch sizes during model fine-tuning and noticed that doubling batch size didn't halve training time: you hit a memory wall or training became I/O bound instead of compute bound. Saturation identification is the inference analogue: finding the batch size where adding more requests stops helping latency.

The aha moment

The saturation point is <strong>not fixed per model</strong>: it's a function of request distribution, sequence length variance, and KV cache precision. A model saturates at batch_size=64 with uniform length=512, but at batch_size=32 with length distribution [100, 500, 2048]. Many engineers treat saturation as a model property and build inflexible autoscaling policies around it. The real insight: saturation is a <strong>runtime property</strong> that changes as your traffic pattern changes. Systems like vLLM measure it continuously via scheduler queue depth and memory pressure. The most sophisticated inference engines expose saturation metrics (e.g., KV cache fill percentage, scheduler wait time percentile) and use them for dynamic request routing or graceful degradation, not static batch size tuning.

You have two inference endpoints serving the same model. Endpoint A runs with batch_size=32 and achieves p99 latency of 50ms. Endpoint B runs with batch_size=128 and achieves p99 latency of 200ms. You're operating above saturation. If you want to serve more concurrent users without increasing latency, should you (a) increase endpoint A's batch size, (b) add a second endpoint sized like A, or (c) reduce endpoint B's batch size? Explain why in terms of the saturation regime you're in.

Show answer hint

Think about which endpoint is operating in the memory-bound region. Adding work to a memory-bound system increases latency; adding a system in the compute-bound region increases throughput. Which regime allows you to absorb more work efficiently?
